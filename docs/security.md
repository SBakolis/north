# Security

North modifies user-level OpenCode configuration and installs executable plugin
code, so installation should be treated as a trusted local administration action.

## Trust and Release Verification

Official release archives contain one statically linked `north` executable. The
agents, instruction fragments, and TypeScript guardrail plugin are embedded at
build time and extracted during configuration. Releases provide SHA-256 values
in `checksums.txt`. Verify the downloaded archive before extraction and obtain
the checksum over a trusted TLS connection to the official release page.

Release artifacts are not currently cryptographically signed and there is no
provenance attestation or self-update channel. A checksum downloaded from the
same compromised location as an archive does not protect against compromise of
that location. Pin versions in managed environments and retain independently
recorded checksums where stronger assurance is required.

## Filesystem Boundary

North resolves all mutable roots from the user's home directory and XDG variables
and requires those roots to be absolute. It writes configuration and snapshots
with owner-only permissions and creates parent directories with owner-only
permissions. Installed OpenCode agent and plugin entries are symlinks to
versioned copies under the North data directory.

The manifest records every managed path, expected regular-file hash, and symlink
target. Installation refuses to replace unowned agent or plugin destinations,
and uninstall refuses to remove managed paths that have changed. These checks
reduce accidental data loss; they are not a sandbox and do not defend against an
attacker already able to modify the user's files or process environment.

Review `north install --dry-run`, `north configure --dry-run`, or `north uninstall
--dry-run` before mutation. Dry-run performs planning and reads local state but
does not write files. Never run North with `sudo`: elevated execution changes its
home and ownership boundary and unnecessarily increases impact.

## Sensitive Data

Stable instruction backups beside the OpenCode configuration, generated merge
bases, and private snapshots under the North state directory may contain the
user's complete OpenCode instructions. Keep them owner-readable, exclude them
from source control and support bundles, and protect them with the same controls
as the originals. North intentionally preserves stable backups after uninstall,
so remove them manually only after verifying they are no longer needed.

The installation manifest exposes local paths, selected components, and version
metadata. `north doctor --json` can expose the same installation metadata and
specific unhealthy paths. Redact these outputs before sharing them publicly.

## External Programs and Generated Code

North requires `git` and `opencode` to be found on `PATH`; selecting OpenSpec also
requires `npx openspec`. Orchestration executes OpenCode workers, Git operations,
and approved acceptance commands with the user's privileges. Review every plan
and its canonical hash before approval. Shell criteria remain disabled unless
the identical plan hash is explicitly approved.

The installed `north-guardrails.ts` plugin is executable code loaded by OpenCode.
Review the North version and source before enabling it in a sensitive environment.
Agent instructions and guardrails reduce accidental unsafe actions but cannot
provide process, filesystem, network, or credential isolation. OpenCode retains
the privileges of the user that launched it.

Do not place secrets in goals, plans, agent prompts, acceptance command arguments,
or instruction files. Runtime logs redact common credential patterns and known
configured secret values, but heuristic redaction is not a security boundary and
cannot protect model provider requests, Git history, arbitrary file contents, or
unrecognized secret formats.

## Known Limitations

- Release checksums are unsigned and no SBOM is currently published.
- Installation is global to the user's OpenCode configuration; project-local
  installation is not supported.
- Configuration is generated by lifecycle flags. Arbitrary manual edits are not
  a supported configuration mechanism and make the managed file unhealthy.
- Lifecycle rollback is best effort within one running process and is not a
  crash-consistent transaction.
- `doctor` is read-only and returns non-zero for actionable errors; advisories do
  not fail the command.
- North provides no sandbox against malicious repositories, acceptance commands,
  model output, OpenCode plugins, or compromised external executables.

## Reporting Vulnerabilities

Do not open a public issue containing exploit details, secrets, private
instructions, or snapshots. Use GitHub's private vulnerability reporting for the
repository when available. Include the affected North version, platform, minimal
reproduction, and expected impact, with all credentials and private paths
redacted.
